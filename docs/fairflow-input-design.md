# FairFlow 판별 입력 설계

FairFlow의 검사 입력을 **여정 기록**과 **모델 입력**으로 나눈다. 여정 기록은 화면과 상호작용에서 확인한 사실 및 출처를 보존한다. 모델 입력은 그 사실을 유형별로 계산한 숫자와 판정 보류 사유를 담는다. 첫 적용 범위는 **한국어·원화 순차공개 가격책정**으로 잡는다. 사전선택과 계층구조도 같은 기록 구조를 사용한다. 이 문서는 구현 전 설계다.

```
Figma 레이어와 프로토타입
  → 1단계 여정 기록
  → 2단계 유형별 모델 입력
  → 로지스틱 회귀 점수 또는 추가 확인 요청
```

## 1단계 · 여정 기록

**하나의 기록은 한 상품·옵션·수량으로 도달하는 한 구매 경로**를 다룬다. 배송 지역, 멤버십 자격, 결제수단처럼 비용을 바꾸는 조건이 확인됐으면 함께 기록한다. 대상이 다른 상품이나 서로 다른 결제 합계를 가진 분기는 각자 기록한다. 대표가와 결제 명세를 같은 상품의 값으로 연결할 수 없으면 그 쌍은 보류한다.

| 필드 | 기록하는 값 |
| --- | --- |
| `schemaVersion`, `pathId`, `scanRevision` | 기록 형식의 버전, 경로 ID, 검사 시점의 스냅샷 ID |
| `scope` | 동일 상품·옵션을 연결하는 키, 수량, 통화, 적용 조건. 확인되지 않은 값은 미확인 |
| `states`, `transitions` | 처음 본 화면에서 결제까지의 상태와 순서. 상태에는 논리적 상태 ID와 Figma 프레임 ID를, 전이에는 트리거·근거·확인 여부를 기록 |
| `observations` | 가격의 역할과 금액, 옵션의 초기 상태, 선택지의 크기·대비·노출 여부, 동작 후 상태 |
| `evidence` | Figma 프레임과 레이어 ID, 필요할 때 문자 범위. 공개 사례를 옮길 때는 문서 URL·쪽 번호·화면 위치 |
| `issues` | 해당 경로에서 확인되지 않았거나 서로 충돌하는 필드와 사유 |

금액은 통화가 확인된 경우 정수 원 단위로 저장한다. 예를 들어 한 텍스트 레이어에 취소선 정가와 판매가가 섞여 있으면 문자 구간을 분리한다. 가격 역할은 `current_price`, `struck_price`, `conditional_price`, `fee`, `checkout_total`로 기록한다. 취소선 정가는 근거로 남기고, 대표가는 같은 상품 카드의 현재 구매 가능한 가격으로 선택한다. 후보가 여러 개면 어떤 가격으로 진행했는지 근거를 확인한다. [Figma 텍스트 구간 API](https://developers.figma.com/docs/plugins/api/properties/TextNode-getstyledtextsegments/)

비용별로 **처음 화면에 보인 위치**, **대표가에 포함됐는지**, **이 주문 조건에서 필수인지**, **첫 가격 당시 금액을 계산할 수 있었는지**를 각각 기록한다. 예를 들어 상세의 `1개당 40,000원`으로 금액과 단위는 읽을 수 있다. 무료 조건이나 주소 조건이 확인되지 않으면 필수 여부와 산정 가능 여부에는 미확인이 남는다.

관찰값은 `{ status, value, source, evidenceIds }` 형태로 기록한다. 상태는 `known`, `unknown`, `conflict`다. 미확인 또는 충돌 상태의 값은 `null`이다. 확인된 `false`와 수량 `0`은 그대로 기록한다. 출처 값은 `figma_layer`, `public_capture`, `derived`, `prototype_run`, `designer_confirmed`를 사용한다. 문구나 금액으로부터 계산한 값은 근거 ID를 남긴다.

같은 Figma 프레임에서도 옵션이나 변수 값이 바뀌면 별도 여정 상태로 표현한다. 계획된 반응은 읽어 기록하고, 적용 조건이 불명확하면 실행 결과를 미확인으로 둔다. 스크롤 영역과 첫 뷰포트를 모두 확인한 경우에만 ‘첫 화면에 보임’을 계산한다. [Figma 프로토타입 반응 API](https://developers.figma.com/docs/plugins/api/properties/nodes-reactions/)

### 공정위 의류 사례를 옮긴 여정 기록

아래는 가격 관련 관찰만 발췌한 예시다. `evidenceIds`는 자료의 목록·상세·결제 캡처를 가리킨다. [공정위 시정 자료 12쪽](https://www.ftc.go.kr/www/downloadBbsFile.do?atchmnflNo=51687#page=12)

```json
{
  "schemaVersion": "journey-evidence@1",
  "pathId": "apparel-order",
  "scope": { "offerKey": "apparel", "quantity": 1, "currency": "KRW" },
  "observations": {
    "firstOffer": { "amountKrw": 62000, "role": "current_price", "evidenceIds": ["list.sale"] },
    "referencePrice": { "amountKrw": 125000, "role": "struck_price", "evidenceIds": ["list.reference"] },
    "delivery": {
      "amountKrw": 40000,
      "basis": "per_item",
      "firstShownStateId": "detail",
      "includedInFirstPrice": false,
      "requiredForOrder": { "status": "unknown", "value": null },
      "calculableAtFirstOffer": { "status": "unknown", "value": null },
      "explicitOptIn": { "status": "unknown", "value": null },
      "evidenceIds": ["detail.delivery", "checkout.delivery"]
    },
    "checkout": { "totalKrw": 102000, "evidenceIds": ["checkout.total"] }
  }
}
```

## 2단계 · 모델 입력

같은 여정 기록에서 선택한 유형에 필요한 관찰을 꺼내 한 개의 모델 입력을 만든다. `featureVersion`은 특징의 **이름, 순서, 단위, 계산식**을 지정한다. 이름 있는 숫자를 버전에 등록된 순서대로 펼쳐 모델에 전달한다. 모델 입력에 원문, 레이어 ID, 사용자 확인 출처, 정답 라벨을 넣는 대신, 패널에서 근거를 찾을 수 있도록 같은 패킷의 메타데이터에서 참조한다.

| 유형 | 숫자를 만드는 방법 | 계산을 보류하는 조건 |
| --- | --- | --- |
| 가격책정 | 가격 증가분과 필수·확정 비용을 각각 결제 합계로 나눈 값, 첫 판매가와 합계의 일치 여부, 첫 화면 비용 공개 비중, 사용자가 직접 고른 비용 여부 | 동일 상품·수량의 합계를 연결할 수 없거나, 설명되지 않는 금액 차이의 조건을 확인할 수 없음 |
| 사전선택 | 추가 유료 옵션 중 처음부터 선택된 비중, 해당 옵션을 사용자가 명시적으로 고른 경로가 확인됐는지 | 옵션이 유료인지, 해당 상태가 첫 진입인지, 사용자의 선택 뒤 상태인지 모호함 |
| 계층구조 | 비교할 두 선택지의 면적·글자 크기·대비 비율과 기본 선택지의 대비·불투명도 | 같은 결정에 대한 선택지인지, 각 동작이 실제로 무엇을 하는지, 의미 있는 시각적 수치를 얻었는지 모호함 |

**가격책정 v1 계산식**에서는 가격 증가 비중을 `(결제 합계 - 첫 판매가) / 결제 합계`로 계산한다. 필수·확정 비용 비중은 `첫 가격 시점에 계산 가능했던 필수 비용 / 결제 합계`다. 첫 화면 비용 공개 비중의 분모는 결제에서 식별한 비용의 합이다. 분자에는 첫 화면에서 같은 금액을 표시했거나 해당 비용의 포함 여부를 표시한 결제 항목의 금액을 더한다. 비용이 없다고 확인된 경로의 공개 비중은 v1과 동일하게 `0`으로 처리한다. 비용이 있었는지 미확인인 경우는 보류한다. 이 값들과 가격 일치 여부, 명시적 선택 여부를 기존 특징 순서로 사용한다. [현재 특징 계산 코드](../src/model-features.js)

다음은 위 의류 사례의 모델 입력이다. 원문 경로에서 확인 가능한 값은 패널에 보여줄 수 있지만 필수 값이 비어 있으므로 점수는 계산하지 않는다.

```json
{
  "pattern": "drip_pricing",
  "featureVersion": "drip_pricing@1",
  "pathId": "apparel-order",
  "status": "needs_context",
  "features": {
    "price_increase_fraction": 0.39215686274509803,
    "first_price_matches_total": 0,
    "required_fixed_fee_fraction": null,
    "fee_visible_at_first_price": 0,
    "explicit_optional_selection": null
  },
  "blockingFacts": [
    "delivery.requiredForOrder",
    "delivery.calculableAtFirstOffer",
    "delivery.explicitOptIn"
  ],
  "evidenceIds": ["list.sale", "detail.delivery", "checkout.delivery", "checkout.total"]
}
```

이 주문에서 40,000원이 필수이고 첫 가격 시점에 계산할 수 있으며 선택한 별도 비용이 없다고 확인된 경우, 모델은 순서대로 `[40000/102000, 0, 40000/102000, 0, 0]`을 받는다. 계산 과정이나 적용 범위가 확인되지 않으면 `needs_context`를 유지한다. 그 사유는 해당 경로와 유형에만 적용한다.

## 플러그인 화면

1. 검사 결과에서 **확인한 내용**을 먼저 보여준다. 예시 카드에는 ‘첫 판매가 62,000원’, ‘상세에서 배송비 40,000원 표시’, ‘결제 합계 102,000원’을 표시하고 각각 근거 레이어로 이동할 수 있게 한다.
2. 점수 계산이 멈춘 경우 해당 경로에만 **확인할 내용**을 연다. 먼저 ‘이 주문에서 이 배송비가 반드시 붙나요?’를 묻고, 필요한 경우 ‘첫 가격을 표시할 때 같은 주문 조건에서 이 금액을 계산할 수 있었나요?’를 이어서 묻는다. 선택 비용이라고 확인되면 사용자가 누른 항목을 경로에서 확인한다. 그 기록이 없을 때만 직접 추가했는지 묻는다. 답변은 **예 / 아니요 / 모름**으로 구성한다.
3. 답변은 현재 경로·검사 버전·근거에 연결한다. 이 값으로 영향을 받는 유형만 다시 계산한다. 근거 레이어나 주문 조건이 바뀌면 관련 답변을 재확인한다. 서로 충돌하는 출처는 보여 주고 확인이 끝날 때까지 점수를 보류한다. 근거 이동 버튼은 해당 검사에서 검증된 프레임·레이어 쌍에 연결한다.

## 기존 코드에 연결하고 검증하는 순서

1. `readJourney`가 제공하는 화면·연결을 읽어 **여정 기록 변환기**를 추가한다. 기존 원시 여정 객체는 규칙 판정, 근거 이동, 디자인 수정안에서 계속 사용한다. 가격부터 문자 구간의 취소선, 상품 연결, 첫 공개 위치와 결제 명세를 읽는다. [현재 검사 진입점](../src/main.js)
2. 여정 기록을 **특징 계산기**로 변환한다. 학습·공개 사례 평가·플러그인 검사에서 같은 변환과 계산을 사용한다. 기존에 점수가 나온 사례는 기존 숫자 벡터와 점수가 일치하는지 먼저 확인한다. v1과 특징의 의미·순서·단위·전처리가 일치하는 경우 기존 가중치로 전후를 비교한다. 새 특징을 추가하거나 기존 정의를 바꾸면 새 특징 버전으로 학습한다.
3. 가격의 정가·판매가 혼합 레이어, 15만 원 무료배송 경계, 지역별 배송비, 뉴스킨처럼 처음부터 합계를 공개한 경로를 먼저 확인한다. 합계가 달라지는 분기의 값이 섞이지 않는지, 금액 조건에 답하지 않아도 그 사유와 근거가 그대로 보이는지 검증한다. 이후 사전선택에서 `0kg`과 미확인 수량을, 계층구조에서 같은 프레임으로 이어지는 서로 다른 상태를 추가로 검증한다. 시각 정보나 동작이 부족한 사례도 함께 둔다. [공개 사례 목록](../data/public-evaluation.md)
4. 기존 JSONL과 공개 사례는 각각의 출처와 라벨을 유지한다. 새 데이터는 `input`에 여정 기록을, `target`에 별도 검토 라벨을 둔다. 훈련 데이터에서 모델 입력은 여정 기록으로부터 다시 계산한다. 이번 공개 사례는 개선용으로 사용하고, 다른 서비스로 만든 최종 평가 자료에서 **판정 가능 비율, 위험 탐지, 정상 경고, 정보 부족 처리**를 함께 보고한다.
